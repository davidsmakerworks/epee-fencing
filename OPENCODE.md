# Agent Context: Epee Fencing (Godot 4.6)

> This file is for AI coding assistants. It summarizes the project state, architecture, conventions, and planned enhancements.

## Project Overview

A 2D epee fencing game built in **Godot 4.6**. Fencers are rendered using a generated sprite sheet (`assets/sprites/fencer_sheet.png`) with procedural drawing as a fallback if the texture is missing. It is **player vs. AI only** — there is no local multiplayer support yet. The codebase was originally generated by a smaller AI model (Qwen 3 27B) and has been iteratively enhanced.

**Goal:** Fun but authentic. No arcade features (power-ups, super moves). Improvements should stay within the framework of real epee fencing.

## Core Architecture

### Match Flow (GameManager)
```
IDLE  --[start_match]-->  READY  --[start_bout]-->  FOUGHT
  ^                                                    |
  |-----------------[bout_reset]-----------------------|
  |
  FOUGHT  --[hit or halt]-->  POINT  --[halt_timer expires]-->  READY
  |
  FOUGHT  --[period ends, DE]-->  HALF_TIME  --[3s break]-->  READY
```

### Fencer State Machine
States: `IDLE`, `EN_GARDE`, `ADVANCE`, `RETREAT`, `ATTACK`, `LUNGE`, `PARRY`, `RECOVER`, `HIT`, `BEAT_ATTACK`

Key state vars:
- `can_act`: gates new attack/lunge/parry/beat transitions
- `hit_registered`: set on successful attack hit; prevents double-scoring from same hitbox
- `attack_hitbox_active`: true only during scoring frames of attack/lunge/beat
- `in_parry_window`: true during first portion of PARRY state; causes `take_hit()` to bail out (bypassed by `is_beat_attack`)
- `is_beat_attack`: true during BEAT_ATTACK state; bypasses opponent parry window in hit detection
- `is_compound_lunge`: true when lunge was triggered from ADVANCE/RETREAT state
- `compound_lunge_type`: `"advance"` (1.25x speed) or `"retreat"` (0.85x speed)
- `blade_length_override`: temporary hitbox range modifier (-1 for default)

### AI Controller
- Reads `player_fencer` and `own_fencer` references set by `game_scene`.
- Difficulty scales `reaction_time`, `aggression_level`, `preferred_distance`.
- Makes decisions on a timer (`next_decision`) when `own_fencer.can_act`.
- Reacts to player attacks with a randomized parry chance.
- Known issue: AI has **perfect frame information** about player attack states; reaction delay is artificial.

## Recently Implemented (Current Session)

### Compound Footwork (Advance-Lunge / Retreat-Lunge)
- Press `W` (Lunge) while in `ADVANCE` or `RETREAT` state to trigger a compound lunge.
- **Advance-Lunge**: 1.25x lunge speed modifier — covers more distance, aggressive closing action.
- **Retreat-Lunge**: 0.85x lunge speed modifier — reduced range counter-attack from retreat.
- Both triggered via `_start_compound_lunge(type)` which sets flags before calling `_start_lunge()`.

### Beat Attack (Key R)
- Replaces the redundant `fencer1_prepare` action.
- Fast attack (0.12s) with reduced blade range (`blade_length_override = 60px` vs default 90px).
- **Bypasses parry**: if `is_beat_attack` is true, opponent's `in_parry_window` is ignored in hit detection.
- Faster recovery (0.7x normal recovery time) to encourage aggressive use.
- Creates risk/reward: shorter range means you must be closer, but it beats defensive parries.

### Period / Bout Timer & Match Formats
- `GameManager` now supports `MatchFormat.POOL` (5 touches, 1×3:00 period) and `MatchFormat.DE` (15 touches, 3×3:00 periods).
- Press `M` to toggle format during IDLE state.
- Timer counts down during `FOUGHT` state; displayed in HUD as `M:SS`.
- **Pool**: match ends when time expires or someone reaches 5.
- **DE**: periods end with a 3-second half-time break; score carries over. Match ends at 15 touches or after 3 periods.
- `HALF_TIME` state added to GameState enum; handled in `_process` with auto-transition to READY.

### Lockout Timing (80ms window)
- When a hit is detected, a lockout timer starts.
- If the opponent hits within the window → **double touch**.
- If after the window → ignored.
- Code detects both overlaps **before** applying `take_hit()`, fixing a prior bug where same-frame hits suppressed the second hit.

### Rear Line Penalty
- Fencers can move freely across the center.
- If Player1 steps left of `PISTE_LEFT` → opponent scores. Player2 stepping right of `PISTE_RIGHT` → opponent scores.

### Corps-à-corps Halt
- If fencer distance < `28 px`, bout halts with no score (calls `GameManager.halt_bout("Corps-a-corps")`).
- They reset to on-guard lines.

### Attack Line Classification (High / Mid / Low)
- `AttackLine` enum added to `fencer.gd`.
- Determined by `blade_angle` during attack:
  - `< -10°` = HIGH
  - `> +10°` = LOW
  - Otherwise = MID
- Currently most attacks/lunges register as MID because animations keep blade near horizontal. Low line attacks are rare in practice.
- Lines are passed through scoring and displayed in UI messages.

## Known Issues / Technical Debt

1. **AI has perfect information.** It checks `player_fencer.is_in_attack_state()` directly every frame.
2. **Feints have no mechanical effect.** AI `FEINT` state calls `_own_start_attack()`, identical to a real attack visually and mechanically.
3. **Controls hardcoded.** Only keyboard; no gamepad or rebinding.
4. **No audio.** Completely silent.
5. **Procedural drawing performance.** `_draw()` on fencer is called every frame; fine for two characters but non-scalable.
6. **Blade angle is automatic.** Player has no direct control over High/Mid/Low line — it is animation-driven.
7. **Parry spark effect exists but is unused.** `hit_effect.gd` has `spawn_parry_spark()`; nothing calls it.

## Coding Conventions

- **GDScript style:** snake_case for functions/variables, PascalCase for classes/enums.
- **Fencer state transitions:** `_start_*` functions gate on `can_act` and set `can_act = false`.
- **Hit detection flow:** `game_scene._check_hits()` queries `attack_hitbox_active` and `get_attack_rect()`; `fencer.take_hit()` handles state transition to HIT.
- **Signal pattern:** `GameManager` emits signals (`point_scored`, `bout_halted`, `match_ended`, `bout_reset`); UI and scene nodes connect to them.
- **Draw-order assumption:** fencers use `Sprite2D` with `region_rect` for state-based animation. Procedural `_draw()` remains as a fallback. No CanvasLayers for fencers. UI is a root Control node with standard anchors.

## Important Notes for Future Agents

- The fencer now uses a **`Sprite2D`** node (`_create_or_configure_sprite()`) referencing `res://assets/sprites/fencer_sheet.png` (160×10 frames, 2 rows for blue/red teams). `_draw()` is skipped when the sprite texture is present, but procedural drawing remains as a fallback.
- **Sprite flipping gotcha:** When `facing == -1`, the sprite is flipped with `scale.x = -1`. Because `centered = false`, this pivots around the top-left corner and would visually offset the fencer by one frame width (160 px). `_update_sprite()` compensates by shifting `sprite.position` to `SPRITE_OFFSET + Vector2(FRAME_W, 0)` so the visual body stays aligned with the physics hitbox origin regardless of facing direction.
- Hit detection and blade-trail calculations still use the same math regardless of rendering mode.
- `GameManager` is an **autoload singleton** (`*res://scripts/game_manager.gd`). It persists across scenes.
- `GameManager.match_format` controls bout target (`POOL_MAX_SCORE = 5`, `DE_MAX_SCORE = 15`) and period structure.
- `GameManager.period_time` counts down during `FOUGHT`; `_end_period()` handles Pool (end match) vs DE (half-time then next period).
- The AI controller (`ai_controller.gd`) is a **plain Node** child of Player2, not a script on the CharacterBody2D itself. It delegates to `own_fencer._start_*()`.
- `game_scene.gd` manages **all hit detection**. `fencer.gd` never checks collisions itself.
- The current code uses `move_and_slide()` inside state update functions, then zeroes `velocity` in the next state. This is unusual godot-style (normally velocity is set before `move_and_slide()` in `_physics_process`) but works for the current setup.
- If adding double-touch tie-breaking (priority), it will require either state in `GameManager` or a new UI element to show which fencer has priority.
